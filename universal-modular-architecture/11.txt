## Skill: Arquitectura Modular Universal - Sistema de Organización de Aplicaciones en Componentes Independientes

**Descripción General:**
Implementar un sistema universal, reutilizable y estricto de arquitectura modular que organice cualquier aplicación en componentes independientes, reutilizables y fáciles de probar, evitando que toda la lógica quede concentrada en un único archivo o función; el sistema debe definir una estructura base separando como mínimo configuración, entrada de usuario, escaneo, validación, procesamiento, progreso, caché, almacenamiento de resultados, reportes, errores y utilidades, con contratos claros entre módulos para que cada componente pueda sustituirse sin modificar el resto del sistema; debe proporcionar reglas para definir responsabilidades únicas, interfaces, modelos de datos, inyección de dependencias, manejo común de errores, configuración por entorno y pruebas unitarias, además de establecer qué módulos son obligatorios y cuáles opcionales según el tipo de proyecto; también debe incluir plantillas de directorios, convenciones de nombres, flujo de ejecución por fases, puntos de extensión y una lista de comprobación de calidad para comprobar que la aplicación no mezcla la lógica de negocio con la interfaz, el acceso a archivos o la configuración, permitiendo reutilizar la misma arquitectura en conversores, herramientas CLI, servicios web, analizadores y aplicaciones de automatización, e integrando coherentemente todos los demás skills del ecosistema (**Bootstrap Inteligente**, **Menús Adaptativos**, **Banners**, **Progress Orchestrator**, **SmartScanner**, **IncrementalCache**, **ParallelOrchestrator**, **ValidationOrchestrator**, **MemoryController**).

### **Fase 1: Principios Fundamentales de la Arquitectura**

#### **1.1 Los 7 Principios Rectores:**

**Principio 1: Responsabilidad Única (SRP):**
- Cada módulo tiene una sola razón para cambiar
- Un módulo no debe saber cómo funcionan los demás
- Si un módulo hace más de una cosa, debe dividirse

**Principio 2: Abierto/Cerrado (OCP):**
- Los módulos están abiertos a extensión pero cerrados a modificación
- Nuevas funcionalidades se agregan mediante nuevos módulos, no modificando existentes
- Uso intensivo de interfaces y puntos de extensión

**Principio 3: Inversión de Dependencias (DIP):**
- Los módulos dependen de abstracciones (interfaces), no de implementaciones
- La inyección de dependencias es obligatoria, no opcional
- Facilita testing con mocks y stubs

**Principio 4: Segregación de Interfaces (ISP):**
- Interfaces pequeñas y específicas, no "god interfaces"
- Cada módulo implementa solo lo que necesita
- Composición sobre herencia

**Principio 5: Separación de Preocupaciones (SoC):**
- Lógica de negocio separada de I/O
- UI separada de lógica
- Configuración separada de código
- Errores manejados en un solo lugar

**Principio 6: Mínimo Conocimiento (Law of Demeter):**
- Un módulo solo habla con sus amigos inmediatos
- No encadenar llamadas a través de múltiples objetos
- Facilita refactorización

**Principio 7: DRY con Límites:**
- No repetir lógica, pero tampoco sobre-abstraer
- Una abstracción solo es válida si se usa en 3+ lugares
- Preferir duplicación accidental sobre abstracción prematura

---

#### **1.2 Reglas de Oro de la Arquitectura:**

**Regla 1: Prohibido el "God Object":**
- Ningún módulo puede tener más de 500 líneas de código
- Ningún módulo puede tener más de 10 métodos públicos
- Si se excede, debe dividirse

**Regla 2: Prohibido el Acoplamiento Directo:**
- Los módulos no pueden importar implementaciones concretas de otros módulos
- Solo pueden importar interfaces/contratos
- Excepción: el módulo de composición (raíz)

**Regla 3: Prohibido el Estado Global:**
- No variables globales mutables
- No singletons con estado
- Estado compartido debe gestionarse explícitamente

**Regla 4: Prohibido el I/O en Lógica de Negocio:**
- La lógica de negocio no puede leer/escribir archivos directamente
- La lógica de negocio no puede hacer llamadas de red
- Todo I/O debe pasar por módulos especializados

**Regla 5: Prohibido el Hardcoding:**
- Ningún valor fijo en el código
- Todo configurable vía archivos de configuración
- Rutas, límites, timeouts, mensajes → configuración

**Regla 6: Obligatorio el Manejo Explícito de Errores:**
- Ningún error puede ser ignorado
- Cada módulo define sus propios tipos de error
- Los errores se propagan mediante resultados tipados

**Regla 7: Obligatorio el Testing:**
- Cada módulo público debe tener tests unitarios
- Cobertura mínima del 80%
- Tests de integración para flujos completos

#### **2.2 Convenciones de Nombres:**

**Archivos:**
- `kebab-case.ts` para todos los archivos
- Patrón: `modulo.rol.ts` (ej: `scanner.core.ts`, `cache.manager.ts`)
- Tipos siempre en `*.types.ts`
- Tests en `*.test.ts` o `*.spec.ts`

**Directorios:**
- `kebab-case` para todos los directorios
- Nombre del módulo en singular (ej: `scanner/`, no `scanners/`)

**Clases/Interfaces:**
- `PascalCase` (ej: `SmartScanner`, `MemoryController`)
- Interfaces con prefijo `I` opcional según lenguaje
- Tipos con sufijo `Type` o sin prefijo

**Funciones/Métodos:**
- `camelCase` (ej: `scanDirectory`, `validateInput`)
- Verbos para acciones (get, set, create, delete, process)
- Sustantivos para getters (files, config, status)

**Constantes:**
- `UPPER_SNAKE_CASE` (ej: `MAX_BUFFER_SIZE`, `DEFAULT_TIMEOUT`)

**Variables:**
- `camelCase` descriptivo
- Evitar abreviaciones excepto las universalmente conocidas

**Eventos:**
- `past-tense` (ej: `scan.completed`, `file.processed`)

### **Fase 3: Contratos e Interfaces**

#### **3.1 Principios de Diseño de Contratos:**

**Regla 1: Contratos Estables:**
- Las interfaces públicas no deben cambiar frecuentemente
- Cambios rompen compatibilidad → versionado semántico
- Documentar cada método con su contrato (pre/post condiciones)

**Regla 2: Contratos Mínimos:**
- Solo exponer lo necesario
- Ocultar detalles de implementación
- Principio de mínimo conocimiento

**Regla 3: Contratos Tipados:**
- Todos los parámetros y retornos deben estar tipados
- Usar tipos estrictos, no `any` o `object`
- Validar tipos en runtime si el lenguaje lo permite

**Regla 4: Contratos Inmutables:**
- Los datos que entran/salen no deben mutar
- Retornar copias, no referencias
- Previene bugs sutiles

### **Fase 4: Inyección de Dependencias**

#### **4.1 Principios de DI:**

**Regla 1: Constructor Injection:**
- Todas las dependencias se inyectan en el constructor
- Nunca crear dependencias dentro del módulo
- Facilita testing con mocks

**Regla 2: Interface-Based:**
- Inyectar interfaces, no implementaciones
- Permite cambiar implementaciones sin modificar el código
- Facilita múltiples implementaciones (test, prod, mock)

**Regla 3: Composition Root:**
- Solo un lugar en toda la app donde se crean las instancias
- Típicamente `main.ts` o `app.ts`
- Todo lo demás recibe dependencias inyectadas

**Regla 4: No Service Locator:**
- No usar un contenedor global de servicios
- La inyección debe ser explícita
- Evita dependencias ocultas

#### **4.2 Ejemplo de Composition Root:**

```typescript
// main.ts - Composition Root

import { ConfigLoader } from './config/config.loader';
import { SmartScanner } from './scanner/scanner.core';
import { ValidationOrchestrator } from './validation/validation.orchestrator';
import { ProcessingCore } from './processing/processing.core';
import { ParallelOrchestrator } from './parallel/parallel.orchestrator';
import { MemoryController } from './memory/memory.controller';
import { IncrementalCache } from './cache/cache.manager';
import { ProgressOrchestrator } from './progress/progress.orchestrator';
import { App } from './app';

async function main() {
  // 1. Cargar configuración
  const config = new ConfigLoader();
  const appConfig = await config.load(process.env.NODE_ENV);

  // 2. Crear utilidades base
  const logger = new Logger(appConfig.logging);
  const i18n = new I18nManager(appConfig.locale);

  // 3. Crear módulos de infraestructura
  const progress = new ProgressOrchestrator(appConfig.progress);
  const memory = new MemoryController(appConfig.memory);
  const parallel = new ParallelOrchestrator(appConfig.parallel);
  const cache = new IncrementalCache(appConfig.cache);

  // 4. Crear módulos de dominio
  const scanner = new SmartScanner({ progress, memory, cache });
  const validation = new ValidationOrchestrator({ config: appConfig });
  const processing = new ProcessingCore({ scanner, validation, parallel, memory, progress });

  // 5. Crear módulos de presentación
  const input = new InputHandler({ i18n, config: appConfig });
  const ui = new UI({ banner: appConfig.banner, theme: appConfig.theme });

  // 6. Crear la app principal
  const app = new App({
    config: appConfig,
    input,
    scanner,
    validation,
    processing,
    progress,
    memory,
    parallel,
    cache,
    ui,
    logger,
    i18n
  });

  // 7. Manejo de errores global
  process.on('uncaughtException', (err) => app.handleError(err));
  process.on('unhandledRejection', (err) => app.handleError(err));
  process.on('SIGINT', () => app.handleShutdown('SIGINT'));
  process.on('SIGTERM', () => app.handleShutdown('SIGTERM'));

  // 8. Ejecutar
  await app.run();
}

main().catch((err) => {
  console.error('Fatal error:', err);
  process.exit(1);
});
```

```typescript
    private readonly i18n: II18n,
    private readonly ui: IUI,
    private readonly config: IConfig
  ) {}

  async handle(error: unknown): Promise<void> {
    const appError = this.normalize(error);

    // 1. Loggear
    this.logger.log(appError);

    // 2. Según severidad
    switch (appError.severity) {
      case ErrorSeverity.INFO:
        // Solo log, no mostrar al usuario
        break;

      case ErrorSeverity.WARNING:
        this.ui.showWarning(this.formatForUser(appError));
        break;

      case ErrorSeverity.ERROR:
        this.ui.showError(this.formatForUser(appError));
        break;

      case ErrorSeverity.FATAL:
        this.ui.showError(this.formatForUser(appError));
        await this.gracefulShutdown(appError);
        process.exit(1);
        break;
    }

    // 3. Intentar recuperación si es posible
    if (this.isRecoverable(appError)) {
      await this.attemptRecovery(appError);
    }
  }

  private formatForUser(error: AppError): string {
    const message = this.i18n.t(`errors.${error.code}`, error.context);
    const suggestion = this.getSuggestion(error);
    return suggestion ? `${message}\n💡 ${suggestion}` : message;
  }
}
```

#### **5.3 Result Pattern (Alternativa a Exceptions):**

```typescript
// Patrón Result para operaciones que pueden fallar

export type Result<T, E = AppError> =
  | { success: true; value: T }
  | { success: false; error: E };

export function ok<T>(value: T): Result<T, never> {
  return { success: true, value };
}

export function err<E>(error: E): Result<never, E> {
  return { success: false, error };
}

// Uso en módulos
export class Scanner {
  async scan(path: string): Promise<Result<ScanResult, ScanError>> {
    try {
      const result = await this.doScan(path);
      return ok(result);
    } catch (e) {
      return err(new ScanError('SCAN_FAILED', '...', ErrorSeverity.ERROR, { path }));
    }
  }
}

// Uso en el llamador
const result = await scanner.scan('/input');
if (result.success) {
  // Usar result.value
} else {
  // Manejar result.error
  await errorHandler.handle(result.error);
}
```

#### **7.2 Implementación del Flujo:**

```typescript
// app.ts

export class App {
  constructor(private readonly deps: AppDependencies) {}

  async run(): Promise<number> {
    try {
      // Fase 1: Bootstrap
      await this.deps.bootstrap.run();

      // Fase 2: Inicialización
      await this.initialize();

      // Fase 3: Entrada
      const input = await this.getInput();

      // Fase 4: Validación
      const validation = await this.deps.validation.validate(input, inputSchema);
      if (!validation.valid) {
        await this.showValidationErrors(validation);
        return 1;
      }

      // Fase 5: Descubrimiento
      const scanResult = await this.deps.scanner.scan(input.path, input.scanOptions);

      // Fase 6: Clasificación
      const classification = await this.deps.cache.classify(scanResult.files, input.cacheOptions);

      // Fase 7: Procesamiento
      const processingResult = await this.deps.processing.process(classification.toProcess, input.processingOptions);

      // Fase 8: Almacenamiento
      await this.deps.output.write(processingResult.results, input.outputOptions);
      await this.deps.cache.update(classification);

      // Fase 9: Reporte
      await this.showReport(scanResult, classification, processingResult);

      // Fase 10: Finalización
      await this.shutdown();

      return processingResult.hasErrors ? 1 : 0;
    } catch (error) {
      await this.deps.errorHandler.handle(error);
      return 1;
    }
  }
}
```

#### **8.1 Sistema de Plugins:**

```typescript
// plugins/plugin.interface.ts

export interface Plugin {
  readonly name: string;
  readonly version: string;
  readonly dependencies?: string[];

  // Hooks del ciclo de vida
  onInit?(app: App): Promise<void>;
  onBeforeScan?(context: ScanContext): Promise<void>;
  onAfterScan?(result: ScanResult): Promise<void>;
  onBeforeProcess?(items: ProcessableItem[]): Promise<ProcessableItem[]>;
  onAfterProcess?(result: ProcessingResult): Promise<void>;
  onShutdown?(): Promise<void>;
}

// plugins/plugin.registry.ts

export class PluginRegistry {
  private plugins: Plugin[] = [];

  register(plugin: Plugin): void {
    this.validateDependencies(plugin);
    this.plugins.push(plugin);
  }

  async runHook<H extends keyof Plugin>(hook: H, ...args: Parameters<NonNullable<Plugin[H]>>): Promise<void> {
    for (const plugin of this.plugins) {
      const fn = plugin[hook];
      if (typeof fn === 'function') {
        await (fn as Function).apply(plugin, args);
      }
    }
  }
}
```

### **Conclusión:**

Esta skill transforma la arquitectura de software de un arte subjetivo y propenso a errores en un sistema estructurado, verificable y reutilizable. La Arquitectura Modular Universal proporciona un marco de trabajo completo que puede aplicarse a cualquier proyecto, desde una pequeña CLI hasta un servicio web complejo, manteniendo la misma coherencia y calidad en todos ellos.

Lo más importante de esta skill es que es **meta**: define cómo deben organizarse todos los demás skills del ecosistema. Sin esta skill, los otros skills serían islas de funcionalidad difíciles de integrar. Con ella, todos los skills (Bootstrap, Menús Adaptativos, Banners, Progress Orchestrator, SmartScanner, IncrementalCache, ParallelOrchestrator, ValidationOrchestrator, MemoryController) encajan como piezas de un rompecabezas perfectamente diseñado.

La combinación de principios sólidos (SRP, OCP, DIP, SoC), estructura clara de directorios, contratos bien definidos, inyección de dependencias, manejo centralizado de errores, configuración por entorno, flujo por fases, puntos de extensión y lista de verificación de calidad convierte a esta skill en la **columna vertebral** sobre la que se construyen todas las aplicaciones profesionales del ecosistema. Es la skill que hace que todas las demás funcionen juntas de forma armónica, predecible y mantenible a largo plazo.
